# mn56

Firebat MN56 미니 PC. 이 문서는 `hosts/nixos/mn56/default.nix` 의 각 줄이 왜 있는지와 이 섀시에서 확인한
사실을 모은다. 실제로 겪은 고장의 경위는 [postmortems](../postmortems/) 에 있다.

## 기계 개요와 이 호스트에만 있는 모듈

Ryzen 7 7840HS (Phoenix, RDNA3 780M iGPU). 배터리 없이 늘 AC 전원에 물린 데스크톱 박스.

벤더 공통 AMD CPU/GPU 설정은 `modules/nixos/amd.nix`([벤더 공통 층](../hardware-vendors.md))에 있고,
`default.nix` 에는 이 섀시에만 해당하는 것만 둔다. 7840HS 기계가 하나 더 있으므로, 공통으로 밝혀진 것은
amd.nix 로 올린다.

- `modules/nixos/nginx.nix`: 회사 앱의 폐쇄망 dev/qa 서버 앞 리버스 프록시를 재현한다
  ([nginx](../nginx.md)). 패키지와 유닛만 넣고 `/etc/nginx` 아래 설정은 그 저장소의 배포 스크립트가 관리한다.
- `modules/nixos/libvirt.nix`: Windows 게스트용 libvirt/KVM ([Windows 게스트](../windows-guest.md)). 회사 앱의
  공동인증 서명이 Windows 네이티브 프로그램에서 돌아서, 흐름의 그 절반은 이 호스트에서 직접 돌릴 수 없다.
- 둘 다 common.nix 가 아니라 여기서 import 한다. 그 작업을 하는 기계가 이것 하나뿐이다.
- power-profiles-daemon(common.nix)은 `balanced` 로 뜬다. performance 에 고정해야 하면 프로필을 바꾼다.
- 칩셋 특이사항은 실제로 부팅해 보기 전에는 짐작으로 넣지 않는다. 무선 펌웨어(유닛에 따라 MT7922 /
  RTL8852BE)는 enableRedistributableFirmware 가 넣는데, 생성된 hardware-configuration.nix 가 not-detected.nix 로
  그걸 끌어온다.

## stateVersion

stateVersion 은 "이 기계의 상태 데이터가 만들어진 릴리스"이지 "따라가는 채널"이 아니다. flake 는 계속
nixos-unstable 을 따라가므로 패키지는 그대로 새 버전으로 올라간다.

- `system.stateVersion = "26.05"`: 26.05 설치본으로 깔았고 nixos-generate-config 가 쓴 값이다.
- `home.stateVersion` 은 기본값 26.11(`modules/nixos/home-manager.nix`)로 둔다. 이 기계에는 home-manager 상태가
  없었으므로, 첫 활성화 때 26.05 시절 호환 shim 이 아니라 지금 기본값을 받는 편이 맞다. 두 값은 서로 상관없이 정한다.

## 수면: 2025-03-11 BIOS 에서 켜 둔다

펌웨어가 제공하는 suspend 는 s2idle 뿐이다(dmesg: "ACPI: PM: (supports S0 S4 S5)", S3 없음). 출하 BIOS(1.00,
2024-01-13 빌드)에서는 s2idle 과 hibernate 가 둘 다 고장 나 있었다. BIOS 빌드 2025-03-11 로 플래시한 뒤
([postmortem](../postmortems/2026-08-13-mn56-bios-update.md)) s2idle 은 rtcwake 두 번(90초, 120초)을 통과했다
(진입·복귀 짝이 맞음, RTC 기상이 제때, wifi 정상, 오류 없음). 다만 옛 고장은 긴 사이클에서만 나타났으므로
(2분 hibernate 는 통과, 13.4시간짜리는 커널을 망가뜨림) 짧은 시험으로는 증명되는 게 거의 없다. 그래서 마스크를
풀고 실사용으로 평가한다. 수면이 다시 먹통이 되면 sleep target 마스크 다섯 개를 되살린다(그 블록의 git 이력에
있다).

알아볼 수 있게 남기는 두 고장의 표식:

**s2idle.** journal 이 "PM: suspend entry (s2idle)" 에서 짝이 되는 exit 없이 끊기고, AX200 Wi-Fi 가 먹통으로
돌아온다. warm reboot 내내 "CSR_RESET = 0x10" 다음 "probe with driver iwlwifi failed with error -110". warm
reset 은 M.2 전원 레일을 살려 두므로 완전히 전원을 꺼야만 카드가 풀린다
([postmortem](../postmortems/2026-08-04-mn56-s2idle-wifi.md)).

**hibernate(S4).** resume 은 깨끗이 끝나고("Restarting tasks: Done", "SMU is resumed successfully!") 몇 초 뒤,
snapshot 때문에 밀려났던 버퍼를 처음 건드린 GPU 클라이언트가 이걸 맞는다:

```
list_del corruption. prev->next should be ..., but was 0000000000000000
kernel BUG at lib/list_debug.c:62!
  ttm_resource_fini / ttm_sys_man_free / ttm_resource_free
  amdgpu_bo_move / ttm_bo_validate / amdgpu_cs_ioctl
```

S4 를 견디지 못한 TTM resource LRU 노드다. 태스크가 버퍼 락을 쥔 채 죽고("exited with preempt_count 1"), 그 락을
원하는 것은 전부 native_queued_spin_lock_slowpath 에서 영원히 돈다 — amdgpu 의 atomic commit worker(모니터가 멈춘
프레임에 고정)와 Hyprland(입력 먹통). 커널 7.1.5, GFX 11.0.1 / DCN 3.1.4. 설정으로 고칠 수 없는 드라이버 버그이고
결정적이지도 않다.

**resumeDevice 를 두는 이유.** `hardware-configuration.nix` 의 48G 스왑 파티션은 hibernate 이미지를 담도록
설치된 RAM 에 맞춘 크기다. 수면이 켜져 있으면 suspend-then-hibernate 로 hibernate 에 닿을 수 있다. resumeDevice
가 없으면 hibernate 는 다음 부팅이 복원하지 않는 이미지를 쓰고, hibernate 할 때마다 조용히 데이터를 잃는 전원
재시작이 된다. UUID 는 swapDevices 항목과 같다.

## warm reboot 가 POST 전에 멈춤 (reboot=pci)

출하 BIOS(1.00 01/13/2024)에서 `reboot` 하면 이 박스가 세 번에 한 번쯤 꺼진 채로 남았다: 두 모니터가 잠든 채
아무것도 안 올라오고, 정상 종료→부팅 간격(19-24초) 대신 53분까지 걸렸으며, 복구는 전원 버튼 길게 누르기였다.

고장은 Linux 아래에 있다. 종료는 매번 깨끗하고(journal 이 "Sending SIGTERM to remaining processes..." 까지
amdgpu 불평 없이 남는다), 멈춘 시도는 부팅 기록을 *전혀* 남기지 않는다. `journalctl --list-boots` 가 reboot 를
요청한 세션에서 전원을 껐다 켠 다음 세션으로 바로 넘어간다. 커널이 journald 까지 못 갔으니 멈춘 것은 펌웨어다.

기본 reboot 방식은 ACPI(`/sys/kernel/reboot/type`), 즉 ACPI reset 레지스터에 쓰는 것이다. `reboot=pci` 는
port-CF9 경로로 플랫폼 리셋을 더 강하게 건다. 이 섀시에서 warm reset 이 레일을 살려 두고 장치를 반쯤 초기화된
채로 두는 것(위 s2idle 표식)과 맞는 선택이다.

그래도 멈추면 OS 쪽에서 못 고친다고 결론 내기 전에 `reboot=bios`, 다음에 `reboot=efi` 를 시도한다. systemd 는
종료 길에 SP5100 TCO watchdog 을 10분 타임아웃으로 걸고 해제하지 못하므로("watchdog did not stop!"), 전원 버튼
대신 10분쯤 기다리면 박스가 스스로 리셋될 수도 있다. BIOS 플래시 뒤 `reboot=pci` 를 빼는 재시험은
[BIOS 업데이트 postmortem](../postmortems/2026-08-13-mn56-bios-update.md) 의 남은 일이다.

## BIOS 플래시 도구 (일부러 남김)

벤더의 마지막 업데이트(`_temp/AR6000-MI2_PHX_250311_Firebat_DIS_SEC`, AMI $FID 기준 빌드 2025-03-11, 프로젝트
1AZKH011)에는 Windows 용 플래셔와 함께 UEFI 셸 플래셔가 들어 있어 Windows 가 필요 없다. 버전 *문자열*은 그대로
"1.00" 이라 dmidecode 의 Release Date 로 구별한다.

`boot.loader.systemd-boot.edk2-uefi-shell.enable` 이 systemd-boot 메뉴에서 EDK2 셸(UEFI 펌웨어 위의 명령 셸)을
띄우고, AfuEfix64.efi 와 .rom 을 그 옆 ESP 에 둔다. 이 플랫폼에서는 SPI 가 매핑되지 않아 flashrom 이 Linux 에서
현재 이미지를 백업하지 못하므로, 백업은 플래시 직전 셸에서 한다:

```
FS0:                                    (파일이 안 보이면 map -r)
AfuEfix64.efi mn56-bios-backup.rom /O   (현재 이미지 먼저 덤프)
AfuEfix64.efi AR6000-MI2.rom /p /b /n /k /RLC:E /reboot
```

`/n` 은 NVRAM 을 다시 쓰므로 BIOS 설정과 UEFI 부트 엔트리가 초기화된다. ESP 의 `\EFI\BOOT\BOOTX64.EFI` 가
여전히 systemd-boot 를 띄우고, `nixos-rebuild boot` 가 엔트리를 다시 등록한다.

남겨 두는 이유: 셸 엔트리와 ESP 위의 AfuEfix64.efi, AR6000-MI2.rom, mn56-bios-backup.rom 은 ~96 MiB 와 부트
메뉴 한 줄이면 되고, 합치면 USB 스틱도 네트워크도 필요 없는 상시 재플래시/롤백 경로가 된다. ESP 의 옛 BIOS
백업은 git 이 담지 않는 `_temp` 사본의 예비본도 된다.

## 드라이브 건강 감시 (smartd)와 NVMe 온도

smartd 는 드라이브의 SMART 속성을 주기적으로 검사하다 임계값을 넘으면 알린다(wall + syslog). `modules/nixos/packages.nix`
의 smartmontools 는 `smartctl` CLI 뿐이라 직접 찾아보지 않으면 아무것도 알려 주지 않는다.

이 박스에서 특히 필요한 이유: 작은 섀시에서 NVMe 가 idle ~64 °C 였고, 특별히 하는 일 없이 Thermal Management
T1 전환을 8번(합계 1276 s) 기록했다. power_on_hours 1359 에 M.2 방열판을 달았다:

| | 이전 idle | 이후 idle | 이후 full load |
|---|---|---|---|
| Composite | 59 °C | 50 °C | 62 °C |
| Sensor 2 | 63 °C | 48 °C | 63 °C |

full load 는 `stress-ng --cpu 16 --hdd 2` 120 s. 실행 내내 T1 Trans Count 가 8 에 머물러 스로틀링은 없었다.
방열판 단 뒤의 full load 가 방열판 달기 전 idle 자리에 있다. 단, CPU 부하가 멈춘 뒤에도 NVMe 온도가 ~40 s 동안
계속 올랐으므로 120 s 로는 지속 부하 평형을 확인하지 못한다(더 긴 시험은 안 했다). 그 시점 마모는
percentage_used 1%. 그래서 여기서 smartd 는 지금의 문제가 아니라 추세를 잡는 용도다.

common.nix 가 아니라 여기 두는 이유: autodetect 인데 지원 장치가 없으면 smartd 는 시작부터 실패하고,
galaxy-chromebook-1 의 저장장치가 SMART 를 지원하는지는 확인하지 않았다. 확인되면 위로 올린다. 경보를 데스크톱에
전하는 방법은 공통이라 [nixos-common](../nixos-common.md#smartd-경보가-데스크톱까지-오는-길)에 있다.

## DDR5 SPD 온도 ALARM 은 정상

`sensors` 가 DDR5 SPD 허브 온도 센서에 ALARM (HIGH) 을 늘 띄우는데, 예상된 것이고 쫓을 고장이 아니다:

```
spd5118-i2c-1-51  +61.8 °C  (high = +55.0 °C)  ALARM (HIGH)
spd5118-i2c-1-50  +55.0 °C  (high = +55.0 °C)
```

idle 62 °C, 부하 ~65 °C 이고, 기준은 SPD5118 허브 레지스터에 프로그램된 55 °C "high" 다(모듈 벤더 값인지 BIOS
값인지는 확인하지 않았다). crit 는 85 °C 라 여유가 충분하다. 이 알람은 DIMM 이 문제라기보다 임계값이 보수적이라는
뜻으로 읽는다. 알람을 끄는 lm_sensors 설정은 넣지 않는다. 임계값을 올리면 진짜 과열도 가려지고, 이 알람은 일부러
`sensors` 를 돌리는 사람에게만 보인다.

NVMe 처럼 고칠 수도 없다. DIMM 두 개가 겹친 슬롯에 포개져 있어 방열판을 달 틈이 없다. 남은 기계적 방법은 바닥에
팬을 다는 것인데, 하지 않았다.
