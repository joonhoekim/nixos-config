# 2026-08-04 — 하이프랜드 세션: 에러 없이 실패한 것 다섯

환경: NixOS 26.11, Hyprland 0.56.1 (uwsm), DMS 1.5.3, galaxy-chromebook-1.

"CRT 셰이더가 안 걸리는 것 같다"로 시작해서 다섯 개가 나왔다. 공통점이 하나 있다 —
**전부 에러를 안 냈다.** 로그는 깨끗하고, 명령은 성공을 보고하고, 유닛은 `enabled`
인데 화면에만 아무것도 없다. 그래서 다섯 개 다 "무엇이 잘못됐나"보다 "무엇을 쳐야
보이나"를 찾는 게 일의 전부였다.

---

## 0. 첫 증상은 고장이 아니었다

`Mod+Shift+C` 를 눌러야 켜지는데, 그걸 모르면 "안 걸린다"와 구분이 안 된다.
`hyprland.lua` 의 순환 목록이 `off` 에서 시작하고 로그인마다 거기로 돌아온다 —
배터리로 도는 기기에서 화면 전체 셰이더를 기본으로 켜 둘 이유가 없어서 그렇게
정해 둔 것이다.

**배울 것.** 기본값이 "꺼짐"인 기능은 사용자 입장에서 고장과 똑같이 보인다.
그런 기능은 켜는 방법이 README 와 코드 주석 양쪽에 있어야 한다.

```sh
hyprctl getoption decoration:screen_shader   # set: false 면 아무도 안 건드린 것
```

## 1. DMS 가 한 번도 시작되지 않았다 — systemd 순환 의존

가장 비싼 건이다.

**증상.** `dms.service` 가 `enabled` 인데 `inactive (dead)`. 실패 기록도, 에러도
없다. 바가 없는 맨 하이프랜드 화면.

**원인.** 세션 로그에 그대로 있었다.

```
wayland-session@hyprland.desktop.target: Found ordering cycle:
  dms.service/start after graphical-session.target/verify-active
  after wayland-session@hyprland.desktop.target/start - after dms.service
Job dms.service/start deleted to break ordering cycle
```

고리는 세 변이다.

| # | 변 | 누가 만들었나 |
|---|---|---|
| 1 | `wayland-session@….target` **After** `dms.service` | **우리** — `wantedBy` 를 target 에 걸어서 |
| 2 | `dms.service` **After** `graphical-session.target` | DMS 유닛 자체 |
| 3 | `graphical-session.target` **After** `wayland-session@….target` | uwsm 의 `Before=` |

1 번이 핵심이고, 이게 이 문서에서 제일 값진 한 줄이다:

> **target 은 자기가 `Wants` 하는 유닛에 암묵적으로 `After` 를 붙인다.**
> `systemd.target(5)` — `DefaultDependencies=no` 가 아니면 `Wants=`/`Requires=` 를
> `After=` 로 보강한다. **서비스에는 없는 규칙이다.**

즉 `WantedBy=어떤.target` 은 "저 target 이 뜰 때 나도 떠라"만이 아니라
"**저 target 은 나보다 늦게 떠라**"까지 말한다. 그걸 모르면 1 번 변이 안 보인다.

그리고 systemd 는 고리를 끊을 때 셋 중 하나를 지우는데, 하필 `dms.service` 의
시작 작업을 지웠다. 지워진 쪽이 target 이었다면 세션이 안 떠서 즉시 알았을 텐데,
지워진 쪽이 셸이라 "조용히 없음"이 됐다.

**고침.** target 이 아니라 **서비스**에 건다 (`modules/nixos/hyprland/default.nix`).

```nix
dms.wantedBy = [ "wayland-wm@hyprland.desktop.service" ];   # not …@….target
```

서비스에는 1 번 규칙이 없으니 고리가 안 생긴다. 순서는 그대로 맞는다 — 저 서비스가
DMS 를 끌어오고, DMS 는 자기 `After=graphical-session.target` 대로 뒤에 뜬다.
`../niri` 가 `niri.service` 에 거는 것과 같은 모양이고, 그게 우연이 아니었던 셈이다.

**다음에 빨리 잡는 법.**

```sh
systemctl --user status dms.service              # inactive 인데 실패 기록이 없다 → 순환 의심
journalctl --user -b | grep -i "ordering cycle"  # 결정적. 고리 전체를 찍어 준다

# 고친 뒤: 문제의 변이 사라졌는지 직접 본다 (재로그인 없이 확인 가능)
systemctl --user show wayland-session@hyprland.desktop.target -p After | tr ' ' '\n' | grep dms
```

**주의.** 순환 판정은 **세션이 시작될 때** 계산된다. 리빌드만으로는 지금 떠 있는
세션의 작업 그래프가 안 바뀌므로, 최종 확인은 재로그인이다.

## 2. 레포를 고쳤는데 화면이 안 바뀐다 — "없을 때만 시드"

**증상.** `~/.config/hypr/dms/` 에 파일이 4 개뿐이었다. 레포는 6 개를 시드하는데.
그리고 더 일반적으로: **레포의 `.frag` 를 고치고 리빌드해도 화면은 안 바뀐다.**

**원인.** `modules/shared/rice-seed-helpers.nix` 의 규칙 한 줄이다.

```sh
seed() { [ -e "$2" ] && return 0; ... }
```

라이싱 파일은 Nix 가 관리하지 않는다(스토어 심볼릭 링크면 읽기 전용이라 핫리로드도
설정 GUI 도 못 산다). 그래서 레포는 **시드일 뿐이고 첫 복사 뒤부터 `$HOME` 쪽이
원본**이다. 리싱 도중 리빌드로 저장 안 한 작업이 날아가지 않게 하려고 일부러 그렇게
둔 것이라 이건 버그가 아니다.

대가는 이거다: **레포에 파일을 새로 넣어도, 그 자리를 이미 가진 머신에는 영영 안
들어간다.** 검사 단위가 파일이 아니라 `seed` 에 넘긴 **경로 하나**라서, 디렉터리면
그 안이 비교 대상이 아니다 — 하나라도 있으면 통째로 건너뛴다.

이 기기가 정확히 그랬다. 날짜를 맞춰 보면 분명하다.

```sh
$ git log --diff-filter=A -1 --date=short --format=%ad -- modules/nixos/hyprland/rice/dms/cursor.lua
2026-08-04          # 조각 6 개 전부 같은 커밋(d516dc6, 하이프랜드 모듈이 처음 생긴 그 커밋)
$ stat -c %w ~/.config/hypr/dms
2026-05-31 01:55    # 디렉터리는 모듈보다 두 달 먼저 있었다
```

즉 **시드가 한 번도 안 돌았다.** 5월에 (모듈이 생기기 전 손으로 하이프랜드를 만져
보던 때) 그 디렉터리가 먼저 생겼고, 8월에 모듈이 들어왔을 때 `seed` 는 `[ -e ]` 에
걸려 조용히 비켜 갔다. 거기 있던 4 개는 전부 DMS 가 만든 것이다 — 셋은 머리말에
`-- Auto-generated by DMS` 라 적혀 있고 나머지 하나는 DMS 가 쓴 빈 파일이다. 없던
2 개는 DMS 가 안 만드는 것, 즉 **레포만 줄 수 있는 것**이었다. "6 개 중 4 개" 가
아니라 "시드 0 개 + DMS 가 만든 4 개" 였던 셈이다.

**고침.** 두 방향을 다 뚫었다.

- 레포 → 라이브: `apps/rice-restore hypr` (이번에 `hypr` 대상을 추가했다)
- 라이브 → 레포: `apps/rice-save` (`~/.config/hypr/{hyprland.lua,shaders}` 추가)

이 둘이 없던 동안 하이프랜드 설정은 **회수 경로 자체가 없었다** — 손으로 튜닝한
값이 레포로 돌아갈 길이 없어 조용히 갈라지고 있었다.

단, `~/.config/hypr/dms/` 는 **일부러 양쪽 다 안 넣었다.** DMS 생성물과 레포
자리표시자가 한 디렉터리에 섞여 있어서다 — `rice-restore` 의 복원은 디렉터리를
`rm -rf` 하고 다시 깔기 때문에(레포에서 지운 조각이 라이브에 남지 않게 하려는 것),
그대로 걸면 DMS 가 만든 `colors.lua`·`layout.lua` 를 날린다. 저 2 개는 이번에 손으로
채웠고, DMS 를 재시작해도 지워지지 않는 것까지 확인했다.

**다음에 빨리 잡는 법.**

```sh
apps/rice-save --check       # 레포 대비 라이브가 무엇이 다른지 (아무것도 안 씀)
apps/rice-restore --check    # 반대 방향
```

"고쳤는데 안 바뀐다" 가 나오면 리빌드를 다시 하지 말고 **이 두 줄부터** 친다.

## 3. `hyprctl keyword` 가 통째로 거절당한다

**증상.** 문서와 위키가 알려주는 대로 쳤는데:

```
$ hyprctl keyword decoration:screen_shader ~/.config/hypr/shaders/crt.frag
keyword can't work with non-legacy parsers. Use eval.
```

**원인.** 이 저장소의 하이프랜드는 `hyprland.conf` 가 아니라 **`hyprland.lua`** 로
설정한다. lua 파서를 쓰면 `keyword` 하위 명령 전체가 못 쓰게 된다. 인터넷의
하이프랜드 예제는 거의 다 `.conf` 전제라 그대로 안 붙는다.

**고침.** 남는 길은 `eval` 하나다.

```sh
hyprctl eval 'hl.config({decoration={screen_shader="/path/to/crt.frag"}})'
```

이걸 감싼 게 이번에 추가한 `apps/rice-crt` 다. 덤으로 `hl.get_config()` 로 지금
걸린 값을 읽을 수 있다는 것도 이때 알았고, 그게 다음 항목을 낳았다.

**설계로 옮긴 것.** 원래 키바인드는 lua 안에 카운터(`local crt = 1`)를 들고 있었다.
스위처가 둘(키바인드 + 스크립트)이 되는 순간 그 카운터는 틀린다 — 밖에서 바꾸면
카운터만 낡고, 낡은 카운터로 고른 "다음"은 엉뚱한 데로 뛴다. 그래서 **양쪽 다
컴포지터에게 현재 값을 묻도록** 바꿨다. 상태를 복제하지 않으면 어긋날 수도 없다.

## 4. 주석이 값의 방향을 반대로 적고 있었다

**증상.** "비네트를 줄여 달라"는데, 주석은 이렇게 말한다.

```glsl
// 비네트 지수. 작을수록 가장자리가 깊게 죽는다.
#define VIGNETTE    0.30
```

시키는 대로 읽으면 **키워야** 약해진다.

**원인.** 쓰이는 자리는 이렇다.

```glsl
col *= smoothstep(0.0, 1.0, pow(max(e.x * e.y, 0.0) * 30.0, VIGNETTE));
```

`pow(x, p)` 에서 `0 < x < 1` 이면 `p` 가 **작을수록 결과가 1 에 가까워진다**. 즉
지수가 작을수록 덜 어두워진다 — 주석과 반대다. 가장자리(밝기 기여 `x` 가 작은
곳)에서 계산해 보면 바로 나온다.

| `uv.x` (0.5=가운데) | 0.5 | 0.15 | 0.05 | 0.02 |
|---|---|---|---|---|
| `VIGNETTE 0.30` | 1.000 | 0.999 | 0.825 | 0.593 |
| `VIGNETTE 0.06` | 1.000 | 1.000 | 0.990 | 0.967 |

**고침.** 값을 1/5(`0.30 → 0.06`)로 내리고 주석을 뒤집었다. 같은 문장이
`modules/shared/ghostty/shaders/crt.glsl` 에도 있다 — 거기서 이식하며 딸려온 것이다.

**배울 것.** "클수록/작을수록" 을 주석에 적을 때, 그 값이 **곱해지는 계수인지
지수인지**를 보고 적어야 한다. 계수는 직관이 맞지만 지수는 밑이 1 보다 작으면
방향이 뒤집힌다. 검산은 3 줄이면 된다.

```sh
python3 -c "print([round((0.147)**p, 3) for p in (0.30, 0.06)])"
```

## 5. 시스템이 얼어붙은 줄 알았다 — 진단 도구가 만든 증상

**증상.** 화면 전체가 멈췄다. 입력도 안 먹는 것처럼 보여 강제 재시작했다.

**원인.** 조사 중에 이걸 돌렸다.

```sh
hyprshot -m output -z ...
```

`-z` 는 **화면을 얼려서 오버레이로 띄운 뒤** 선택을 기다리는 옵션이다. 그런데 이
기기는 터치패드가 죽어 키보드 전용이라 포인터 선택이 영영 안 끝난다. 시스템은
멀쩡했고, 얼어붙은 스크린샷 한 장이 화면을 덮고 있었을 뿐이다.

증거로 이전 부팅 로그를 봤다 — i915 GPU hang 도, 리셋도 없고 종료는 정상
poweroff 시퀀스였다. 셰이더는 무관했다.

```sh
journalctl -b -1 -p warning      # 직전 부팅에서 진짜 죽었는지 확인
```

**배울 것.** 포인터가 없는 기기에서 **포인터 선택을 요구하는 도구**는 진단 도구가
아니라 새 고장이다. `-z` 같은 "화면을 얼린다" 옵션은 특히 위험하다 — 실패 모드가
"시스템 정지"와 똑같이 생겼다.

## 공통점

다섯 개 중 넷이 같은 모양이다.

**성공을 보고하는 실패.** `systemctl` 은 유닛이 `enabled` 라 하고, 리빌드는
`Done.` 이라 하고, `hyprctl eval` 은 `ok` 를 돌려주고, 셰이더 컴파일 실패는
하이프랜드가 다음 프레임에 조용히 삼킨다. 이 층들은 서로 "내 몫은 했다"고 말하지만
아무도 화면을 안 본다.

그래서 이 저장소에서 "고쳤는데 안 바뀐다"를 만나면 순서가 이렇다.

1. **라이브 파일이 실제로 바뀌었나** — `apps/rice-save --check`
   (레포를 고친 것과 화면이 읽는 것은 다른 파일이다)
2. **그 파일을 읽는 것이 다시 읽었나** — 스위처를 한 번 돌린다
   (`apps/rice-crt --reload`, `apps/rice-term`, `hyprctl reload`)
3. **그것을 띄우는 유닛이 애초에 떴나** — `systemctl --user status`,
   그리고 `journalctl --user -b | grep -i cycle`

3 번을 마지막이 아니라 처음에 봤다면 1 번 항목은 10 분이면 끝났을 것이다.
