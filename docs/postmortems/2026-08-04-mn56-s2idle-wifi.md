# 2026-08-04 — mn56: s2idle 이 무선 카드를 물고 늘어졌다

환경: NixOS 26.11, 커널 7.1.5, systemd 261, Firebat MN56 (Ryzen 7 7840HS), Intel AX200.

"어제 suspend 시켰는데 아침에 와이파이가 없다. 재부팅해도 없다"로 시작했다.
증상은 네트워크인데 원인은 전원 관리였고, 결정적인 단서는 **로그에 있는 줄이 아니라
없는 줄**이었다.

---

## 증상

전날 저녁 suspend. 다음 날 아침 부팅하니 `wlp4s0` 가 아예 없다. `systemctl reboot`
을 여섯 번 했는데 여섯 번 다 없다. 전원을 완전히 내렸다 올리니 돌아왔다.

---

## 1. 저널이 한 줄에서 그냥 끝난다

`suspend` 를 건 부팅의 마지막 줄이 이것이다.

```
2026-08-03T18:25:48  systemd-sleep[367781]: Performing sleep operation 'suspend'...
2026-08-03T18:25:48  kernel: PM: suspend entry (s2idle)
```

그리고 끝이다. 다음 줄이 없다. `PM: suspend exit` 도, 하다못해 오류도 없다.
다음 부팅에서 journald 가 `system.journal corrupted or uncleanly shut down` 이라고
말한다.

**`entry` 는 있는데 `exit` 이 없다는 건 그 사이에서 죽었다는 뜻이다.** 이 한 쌍이
이 조사의 전부였다. 고장 난 시스템은 자기가 고장 났다고 못 적는다 — 적을 CPU 가
멈춰 있으니까. 그래서 마지막 줄이 무엇인지가 곧 사인(死因)이다.

---

## 2. hibernate 는 실행조차 안 됐다

당시 설정은 모든 suspend 를 `suspend-then-hibernate` 로 보내고 있었다. 3 시간 뒤
RTC 로 깨어나 hibernate 하는 구조다. 그래서 처음엔 hibernate 이미지 쓰기가 문제인
줄 알았는데, 아니었다.

```
kernel: PM: Image not found (code -22)          # 다음 부팅, 스왑에 이미지가 없다
$ ls /sys/firmware/efi/efivars/ | grep -i HibernateLocation
(없음)                                           # systemd 가 hibernate 를 시작도 안 했다
```

스왑 파티션에 swsusp 시그니처가 없다 = **이미지가 쓰인 적이 없다.** hibernate 단계에
도달하지 못했다는 뜻이다.

그럼 어디서 죽었나. RTC 레지스터에 답이 남아 있었다.

```
$ grep -E 'alrm|alarm_IRQ' /proc/driver/rtc
alrm_time : 12:25:48        # UTC. = 8/3 21:25:48 KST, suspend 시각 + 정확히 3h
```

알람은 정상적으로 무장됐다. 즉 **21:25 에 깨우려던 그 순간, s2idle 에서 빠져나오는
길에서 멈췄다.** hibernate 는 그 뒤에 올 예정이었고 오지 못했다.

---

## 3. 이 경로는 그날 처음 돌았다

왜 하필 그날인가. 로그를 뒤로 감아 보면 이 기능이 들어온 뒤 실제로 RTC 기상까지 간
적이 한 번도 없다.

| 날짜 | 무엇 | 결과 |
|---|---|---|
| 8/1 10:42 | 손으로 `systemctl hibernate` | 60 초 뒤 복귀. **성공** |
| 8/1 18:40 | suspend → 1 시간 뒤 손으로 깨움 | 알람(3h) 전이라 **기상 leg 안 탐** |
| 8/3 18:25 | suspend → 3h 알람 만료 | **행** |

기능을 넣은 커밋은 8/1 이고, 그날의 테스트는 두 번 다 hibernate 경로만 만졌거나
알람이 울리기 전에 손으로 깨운 것이었다. **"테스트했다"고 생각한 것과 실제로 실행된
코드 경로가 달랐다.**

---

## 4. 진짜 함정: `CSR_RESET = 0x10` 은 범인이 아니다

망가진 부팅의 iwlwifi 로그는 이렇게 시작한다.

```
iwlwifi 0000:04:00.0: CSR_RESET = 0x10
iwlwifi 0000:04:00.0: Host monitor block 0x0 vector 0x0
  … 레지스터 덤프 수십 줄 …
iwlwifi 0000:04:00.0: probe with driver iwlwifi failed with error -110
```

첫 줄만 보고 "이게 원인이다" 하면 틀린다. **정상 hibernate 사이클에서도 똑같이
나온다.** 8/1 의 성공한 hibernate 와, 고친 뒤 8/4 의 성공한 hibernate 양쪽에서
확인했다.

```
10:35:54  iwlwifi 0000:04:00.0: CSR_RESET = 0x10   ← 나온다
10:35:58  wlp4s0: associated                        ← 그래도 4 초 뒤 붙는다
```

판별자는 첫 줄이 아니라 **그 뒤에 레지스터 덤프와 `-110` 이 따라붙는지**다.
세는 게 제일 빠르다.

```sh
journalctl -b -k | grep -c 'probe with driver iwlwifi failed'   # 0 이면 정상
```

---

## 5. 재부팅으로는 안 풀린다

이게 "재부팅해도 안 된다"의 정체다.

| 무엇 | 횟수 | 결과 |
|---|---|---|
| `systemctl reboot` | 6 | 전부 `-110` |
| `systemctl poweroff` → 전원 투입 | 1 | **정상** |

M.2 카드는 warm reset 으로 전원 레일이 안 내려간다. 카드가 리셋에 물린 상태는
PCIe 를 다시 열거해도 그대로 살아남고, **레일을 실제로 내려야** 풀린다.

아침에 머신을 어떻게 올렸는지는 로그에 안 남아서 모른다. 확실한 건 그 뒤의 재부팅
여섯 번이 전부 실패했고 완전한 전원 차단 한 번이 고쳤다는 것이다.

> 이 증상을 만나면 **재부팅하지 말고 전원을 내린다.** 재부팅은 시간만 버린다.

---

## 고침

s2idle 을 경유하지 않는다. `hosts/nixos/mn56/default.nix` 에서 동사만 바꿨다.

```nix
systemd.services.systemd-suspend.serviceConfig.ExecStart = [
  ""
  "${config.systemd.package}/lib/systemd/systemd-sleep hibernate"   # was: suspend-then-hibernate
];
```

`HibernateDelaySec` 은 같이 지웠다 — `suspend-then-hibernate` 가 없으면 지배할
대상이 없다.

이 박스는 `ACPI: PM: (supports S0 S4 S5)` 라 S3 가 없다. suspend 는 무조건 s2idle
이고, 배터리도 없어서 s2idle 이 벌어 주는 것도 없었다. 경유할 이유 자체가 없다.

**아직 안 막힌 구멍이 하나 있다.** `systemd-suspend-then-hibernate.service` 는 별개
유닛이고 손대지 않았다. DMS 의 suspend behavior 를 `SuspendThenHibernate`(2) 로
바꾸면 그 유닛이 뜨고 다시 s2idle 로 들어간다. `acSuspendBehavior` 는 `0` 으로 둔다.

검증 (8/4 10:33, DMS 전원 메뉴에서):

```
systemd-logind: suspend requested from client PID 87729 ('systemctl')   ← DMS 경로
systemd-sleep:  Performing sleep operation 'hibernate'...               ← 실제 동작
PM: hibernation: hibernation entry … hibernation exit
wlp4s0: associated
```
`PM: suspend entry (s2idle)` 는 한 줄도 안 나왔다.

## 다음에 빨리 잡는 법

```sh
# 1. suspend/hibernate 가 어디까지 갔나. entry 만 있고 exit 이 없으면 거기서 죽은 것
journalctl -b -1 -k | grep -E 'PM: (suspend|hibernation) (entry|exit)'

# 2. hibernate 가 이미지를 실제로 썼나 (다음 부팅에서 본다)
journalctl -b -k | grep 'PM: Image'      # "Image not found" → 안 썼다 = 실행 안 됨
ls /sys/firmware/efi/efivars/ | grep -i HibernateLocation

# 3. 복원 성공 판정. boot ID 가 유지되면 성공, 새 ID 면 이미지가 안 살아난 것
journalctl --list-boots | tail -3

# 4. RTC 알람이 언제로 잡혔었나 (suspend 시각과 대조하면 어느 leg 인지 나온다)
grep -E 'alrm|alarm_IRQ' /proc/driver/rtc

# 5. NIC 가 진짜 물렸나. CSR_RESET 줄만 보고 판단하지 않는다
journalctl -b -k | grep -c 'probe with driver iwlwifi failed'
```

## 배울 것

**저널의 마지막 줄이 사인이다.** 전원 관리 사고는 에러를 안 남긴다. 남길 CPU 가
멈춰 있어서다. `entry`/`exit` 처럼 짝이 있는 로그를 찾아서 짝이 맞는지 보는 게
"에러 검색"보다 빠르다.

**손으로 깨운 테스트는 타이머 leg 을 테스트한 게 아니다.** 이번 건의 본질은
"3 시간 뒤 무인 상태에서만 도는 코드"를 한 번도 안 돌려 보고 배포한 것이다. 지연
시간이 있는 기능은 지연을 몇 분으로 줄여서 눈앞에서 한 번 돌려 본다.

**같은 로그 줄이 정상에도 나온다면 그건 판별자가 아니다.** `CSR_RESET = 0x10` 처럼
전이 과정에서 늘 나오는 줄을 원인으로 붙잡으면, 정상 사이클을 고장으로 오진한다.
의심되는 줄은 **성공한 사이클의 로그에도 있는지** 먼저 확인한다.
